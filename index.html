🔎 Focus / Tabindex 測試頁

比較「原生 <button>」與「<div> 模擬按鈕」在鍵盤操作上的差異

請只用鍵盤操作測試：
  1. 用滑鼠點一下網址列或頁面空白處，讓焦點離開所有按鈕
  2. 按 Tab 鍵，觀察焦點是否會依序移到每一顆按鈕上（橘色外框）
  3. 焦點停在按鈕上時，分別按 Enter 和 空白鍵，觀察下方訊息是否有反應

🎯 寫法四：tabindex="-1"

tabindex="-1" 的元素不會出現在 Tab 順序中， 但可以用 JS 呼叫 .focus() 主動把焦點移過去。 常見情境：點擊按鈕後，把焦點移到剛出現的訊息／面板，方便鍵盤與螢幕報讀器使用者馬上知道發生了什麼事。

💡 實驗看看：把區塊二任一顆 div 的 tabindex="0" 刪掉（打開瀏覽器開發者工具修改），再用 Tab 鍵測試， 會發現該按鈕直接從 Tab 順序中「消失」，鍵盤使用者完全無法選到它。

🙈 觀念五：焦點順序要跟視覺順序一致

Tab 順序永遠跟著 HTML 撰寫順序（DOM 順序） 走，跟畫面「看起來」的排列無關。 如果只靠 CSS 把畫面翻轉，會造成焦點順序跟視覺順序對不上。

❌ 錯誤示範：HTML 順序是 A、B、C，但用 CSS flex-direction: row-reverse 讓畫面看起來變成 C、B、A

✅ 正確示範：畫面同樣是 C、B、A，但直接把 HTML 也寫成這個順序，不靠 CSS 硬翻轉

🔒 觀念六：焦點陷阱（Focus Trap）

對話框開啟時，Tab／Shift+Tab 應該只在對話框內的元素間循環， 不能跳到背景頁面；按 Esc 或關閉後，焦點要「歸還」給原本觸發它的按鈕。

🎹 觀念七：Roving tabindex（複合元件方向鍵導覽）

一組相關的選項中，只有「目前作用中」的項目 tabindex="0"，其餘都是 tabindex="-1"。 先按一次 Tab 進入這組元件，之後改用 ←/→ 方向鍵切換， 不需要每個選項都 Tab 一次。這正是排序類、可重組類元件（例如重組句子遊戲）最常用的模式。

📢 觀念八：aria-live 動態內容播報

畫面內容被 JS 動態更新、但使用者的焦點沒有跟著移動時（例如這裡按按鈕只更新旁邊的文字）， 螢幕報讀器預設不會發現內容變了。加上 aria-live="polite" 後， 報讀器會在使用者操作空檔自動唸出新內容。視覺上你看不出差異，需要用螢幕報讀器（NVDA / VoiceOver）實測才聽得出來。

⏭️ 觀念九：跳過區塊連結（Skip Link）

頁面開頭如果有很長的導覽選單，鍵盤使用者每次都要 Tab 過所有選單項目才能到主要內容。 加一個「跳到主要內容」的連結（平常視覺上隱藏，Focus 時才顯示）可以讓使用者一鍵跳過。 這裡不需要 JS，純靠 <a href="#id"> 搭配目標元素的 tabindex="-1" 就能運作。

請把焦點移到下面這區最前面（例如點一下這行文字後按 Tab），第一個出現的應該就是跳過連結：

跳到主要內容
首頁 關於我們 服務項目 聯絡方式
🎉 這裡就是「主要內容」。按下上面的跳過連結後，焦點會直接跳到這裡，不用一個一個 Tab 過前面四個導覽連結。

🏷️ 觀念十：可及名稱（Accessible Name）

只用圖示做的按鈕，螢幕報讀器唸不出「這是什麼」，可能只唸出「按鈕」或整個跳過。 一定要用文字、aria-label，或視覺隱藏文字，給元素一個可及名稱。 可以在瀏覽器開發者工具的 Accessibility 面板查看 Name 欄位確認差異。

✅ 正確示範：畫面看起來一樣，但用 aria-label 補上文字說明

🖼️ 觀念十一：<img> 的 alt 與 aria-label 該怎麼搭配

alt=""（空字串）對輔助科技的意思是「這張圖不重要，請直接忽略」。 一個「請忽略我」的元素，不可能同時又是使用者要操作的功能控制項——記住這一點， 下面兩種情境該怎麼寫就能自己推導出來。可以打開瀏覽器開發者工具的 Accessibility 面板， 比對每個元素的 Name 欄位。詳細規則說明見 docs/img-alt-aria-label.md。

✅ 情境一：裝飾圖示包在真正的 <button> 裡，名稱由外層 aria-label 負責，img 維持 alt=""
